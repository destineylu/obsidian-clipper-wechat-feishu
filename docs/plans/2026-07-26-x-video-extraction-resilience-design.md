# X 视频提取韧性修复设计

## 问题

X 帖子页面中的 `<video>` 使用 `blob:` 临时地址。插件需要从
`TweetResultByRestId` 返回的媒体信息或页面已加载的网络资源中找到可移植的视频
地址。X 更新查询标识后，插件仍调用旧接口，过早执行时性能资源兜底也可能为空，
最终只能保留封面或原帖链接。当前 X 页面还不再稳定暴露旧的
`webpackChunk_twitter_responsive_web` 全局变量，导致上一版修复即使发现了新请求，
也可能因无法取得认证信息而在实际请求媒体元数据前提前返回。

## 方案

1. 后台优先调用 X 自己的公开嵌入接口 `cdn.syndication.twimg.com/tweet-result`。
   该接口不需要用户 Cookie，并能直接返回视频的多个 MP4 清晰度。请求使用 X
   嵌入客户端相同的确定性 token 算法，不保存任何凭据。
2. 公开嵌入接口不可用时，复用当前页面已经请求过的 `TweetResultByRestId` 完整
   URL。该 URL 包含 X
   当前使用的查询标识、功能参数和字段开关。
3. 认证信息优先从已有 webpack 模块读取；旧全局变量不可用时，从页面当前加载的
   官方 `responsive-web/client-web/main.*.js` 脚本动态读取，不在仓库中硬编码令牌。
4. 页面尚未暴露该请求时，依次尝试当前已验证的查询标识和旧查询标识。
5. GraphQL 返回多个视频变体时，优先选择最高码率的完整 MP4。
6. GraphQL 不可用时，短时轮询页面网络资源；接受完整 MP4 或主 HLS 播放列表，
   排除音频和分片 MP4。
7. 渲染时按视频封面归组，每个视频只保留最佳候选，避免最后一个 HLS 候选覆盖
   已经取得的 MP4。Obsidian 不能直接播放远程 HLS 时仍可使用 MP4。
8. 所有直接视频探测失败时，继续保留现有的封面和原帖播放链接。

## 验证

- 动态发现当前 `TweetResultByRestId` URL，并选出最高码率 MP4。
- 两个真实帖子通过 X 公开嵌入接口返回完整 MP4 候选。
- 最终笔记只保留最佳 MP4，不会被同一视频的 HLS 播放列表覆盖。
- 旧 webpack 全局变量不存在时，从当前官方主脚本读取认证信息。
- 页面没有已发现请求时，使用当前查询标识兜底。
- 性能资源兜底不会把音频或自适应流分片当成完整视频。
- 原有 X 文章、图片、线程和视频失败回退测试继续通过。
- 使用两个真实 X 帖子进行人工浏览器回归。
